## 1. 产品概述

### 1.1 背景

真实面试经验分散在外部平台与个人笔记中，难以筛选、检索与系统复习。「面个 Offer」把真实面经结构化，让后来的人能搜到、读懂、复制到自己的 AI 里继续学习。

随着产品形态完善，V1 不再只服务个人使用，而是作为一个可公开访问、允许开发者贡献真实面经的 Public Beta 产品。

### 1.2 产品定位

**一个面向开发者的真实面经检索与协作平台。**

用户可以：

- 搜索、筛选并阅读真实面经；
- 直接定位到具体面试问题与追问；
- 将不会的问题复制到自己习惯使用的 AI 中继续学习；
- GitHub 登录后，以结构化方式投稿新的面经；
- 为当前不存在的公司、岗位、标签提出新增项；
- 查看自己的投稿审核状态；
- 对已发布的本人投稿发起修改或删除申请。

平台通过管理员审核与内容治理，持续维护高质量、统一、可检索的面经知识库。

### 1.3 V1 核心闭环

V1 只狠狠干好五件事：

1. **搜索**
2. **阅读**
3. **投稿**
4. **审核**
5. **内容治理**

核心闭环：

```text
游客
  → 搜索 / 筛选面经
  → 阅读问题与追问
  → 复制不会的问题
  → 去自己的 AI 中继续学习

登录用户
  → GitHub 登录
  → 结构化投稿面经
  → 等待管理员审核
  → 审核通过后公开
  → 查看自己的投稿状态
  → 已发布内容需要修改 / 删除时发起申请

管理员
  → 审核投稿
  → 修正任意内容
  → 处理公司 / 岗位 / 标签新增项
  → 发布 / 拒绝
  → 处理已发布内容的修改 / 删除申请
```

### 1.4 产品原则

1. **真实数据优先。** 不为了结构化展示而创造原记录不存在的事实。
2. **问题优先。** 面试问题、追问与轮次是产品主角。
3. **低门槛浏览。** 游客无需登录即可搜索和阅读。
4. **结构化贡献。** 投稿不使用 Markdown 编辑器，不要求用户学习格式。
5. **用户负责贡献事实，平台负责组织知识。** 题目分类、算法识别、知识体系整理由平台后处理（管理员 / 搜索 / 未来的 AI）完成，不交给投稿用户。
6. **管理员拥有最终内容治理权。** 正式公开内容由平台审核后确定。
7. **V1 克制功能边界。** 不为了“看起来完整”堆叠社区、AI、会员等非核心能力。
8. **不让用户理解数据模型。** 投稿表单中任何需要用户先理解系统数据结构才能填写的字段（日期精度、问题类型、题目分组、问题上下文等）都必须重新审视并移出主流程。

## 2. V1 目标与非目标

### 2.1 V1 目标

V1 必须完成：

- 公开浏览真实面经；
- 按公司、岗位分类、招聘类型与关键词筛选；
- 搜索到具体问题与追问，并定位到详情中的对应位置；
- 清晰阅读轮次、问题、追问、算法题与来源；
- 复制单题、追问上下文或整个问题组；
- PC 与手机浏览器均可正常使用；
- GitHub OAuth 登录；
- 登录用户结构化投稿面经；
- 投稿中支持提出新的公司、岗位与标签；
- 管理员审核投稿，并可修改投稿中的全部内容；
- 管理员决定是否创建新的公司、岗位与标签；
- 登录用户查看自己的投稿状态；
- 投稿在审核通过前允许作者修改；
- 已发布投稿支持作者发起修改 / 删除申请，最终由管理员决定；
- 对明确的同源重复投稿进行基础去重；
- 提供统一“关于 / 反馈”入口，展示项目与作者信息、开源仓库、意见反馈入口与自愿赞赏方式。

### 2.2 V1 明确不做

以下内容不进入 V1：

- 评论；
- 点赞；
- 关注；
- 私信；
- 好友 / 社交关系；
- 排行榜；
- 积分体系；
- 收藏与云同步；
- 学习进度；
- 标准答案库；
- 站内 AI 回答；
- AI 审核；
- AI 自动生成面经；
- AI 模拟面试；
- 会员、付费内容与站内商业支付（自愿赞赏二维码除外）；
- 个性化推荐；
- 复杂运营后台；
- 站内反馈工单系统 / 反馈后台；
- 语义搜索 / 向量搜索；
- 基于问题相似度的自动面经去重；
- 最终面试结果字段（Offer / 挂 / 泡池 / 流程中等）。

AI 问答、AI 审核、付费等可以作为后续版本方向，但 V1 不预先实现。

## 3. 用户角色与权限

### 3.1 游客

游客无需登录，可以：

- 浏览面经；
- 搜索；
- 使用公司 / 岗位 / 招聘类型筛选；
- 查看面经详情；
- 复制问题与追问；
- 打开公开面经分享链接；
- 查看原始来源链接。

游客不能：

- 投稿；
- 提出新的公司 / 岗位 / 标签；
- 查看投稿记录；
- 发起已发布内容的修改 / 删除申请。

### 3.2 GitHub 登录用户

登录用户拥有游客全部能力，并可以：

- 投稿面经；
- 在投稿过程中提出新的公司、岗位、标签；
- 查看自己的投稿列表与审核状态；
- 在审核通过前修改自己的投稿；
- 对自己已经发布的投稿发起修改申请；
- 对自己已经发布的投稿发起删除申请。

### 3.3 管理员

管理员拥有平台内容治理权限，可以：

- 查看所有待审核投稿；
- 修改投稿中的任意内容；
- 将用户填写的公司 / 岗位 / 标签改为已有正式项；
- 创建新的正式公司 / 岗位 / 标签；
- 删除无价值或错误标签；
- 发布投稿；
- 拒绝投稿；
- 查看投稿原始内容与当前审核内容；
- 处理已发布内容的修改申请；
- 处理已发布内容的删除申请；
- 直接修改已发布面经（保持已发布状态；存在待处理申请时须先处理申请；修改留有修订审计）；
- 处理明显重复投稿。

## 5. 搜索与筛选

### 5.1 搜索目标

搜索不是简单的“文章标题搜索”，而是帮助用户快速找到：

- 哪家公司问过某个知识点；
- 哪些岗位问过某个问题；
- 面试官是如何提问的；
- 这道题后续还追问了什么。

### 5.2 搜索范围

搜索范围包含：

- 公司；
- 岗位；
- 岗位分类；
- 主问题；
- 追问；
- 标签 / 考点；
- 算法名称；
- 算法原题描述。

备注、作者感受、面试结果等内容不作为问题搜索内容。

### 5.3 V1 搜索规则

- 搜索条件与公司、岗位分类、招聘类型筛选做 AND 组合；
- 去除首尾空白；
- 多处连续空白视为关键词分隔；
- 空搜索词表示不限制搜索；
- 中文按包含匹配；
- 英文大小写不敏感；
- 空白分隔的多个非空关键词全部参与 AND 匹配；
- V1 不做复杂中文分词；
- V1 不做语义搜索；
- V1 不做自动同义词扩展。

例如：

`Redis 分布式锁`

要求一份面经整体能够覆盖 Redis 与分布式锁，但两个词不强制出现在同一道题中。

### 5.4 搜索结果展示

搜索结果仍按“面经”展示，不新增独立问题列表页。

命中具体问题时：

- 卡片最多展示两个有代表性的命中片段；
- 标注所属轮次；
- 点击片段进入详情并定位到对应问题；
- 点击整张卡片默认定位到第一个问题命中位置；
- 搜索进入详情后，高亮当前搜索关键词；
- 高亮只影响视觉，不修改原始文本与复制内容。

如果关键词分散在不同问题中，仍可视为该面经命中，但不能包装成同一道题。

仅命中公司或岗位等元信息时，不伪造问题命中片段。

### 5.5 公司筛选

公司是第一核心筛选维度，V1 单选。

公司列表与数量必须来自数据库，不在前端组件中重复硬编码。

公司数量根据当前其他筛选条件和搜索条件动态计算。

### 5.6 岗位筛选

岗位筛选 V1 单选。

岗位分类 V1 冻结为五类初始目录：

```text
全部
Agent 开发
AI 应用
AI Infra
后端开发
```

「AI 后端」取消：给 AI 产品写服务端的岗位归「后端开发」，模型网关 / 推理 / 调度类归「AI Infra」——边界由岗位内容判断，不保留模糊中间类。「其他」仅作数据兜底，不作为筛选项展示。岗位筛选、标签库、面经归类、首页统计全部复用同一套分类。

方向**目录化**：方向存于 `position_category` 目录表，管理员在确认岗位候选时可从已有方向中选择，也可随手新建（如「算法」）——新方向自动进入首页筛选与统计，不需要改代码发版。普通用户全程不感知方向（只填岗位名）。

### 5.7 招聘类型

V1 单选：

```text
全部
实习
校招
```

历史数据中的日常实习、暑期实习统一归入实习；秋招、春招、提前批、校招统一归入校招。

### 5.8 排序

V1 默认最新优先，不提供排序选择器。

排序依据优先使用该份面经中**最早一轮已经确认的面试时间**（日期精度为月 / 年时按已知部分参与排序）。

日期不完整或不存在时，不补造日期。

## 6. 面经列表卡片

### 6.1 一份面经 = 一张卡片

卡片至少展示：

- 公司；
- 部门（存在时）；
- 岗位；
- 招聘类型；
- 岗位分类；
- 标签（治理后每份面经保留最多 5 个正式标签；卡片最多展示 4 个，行尾渐隐提示更多）；
- 首轮面试日期（存在时）；
- 实际存在的面试轮次；
- 搜索命中片段（存在时）。

部门是可选信息（如「字节跳动 · 抖音电商」），历史数据与新投稿均可携带。

### 6.2 面试时间

面试时间按**轮次**记录，而不是整份面经只有一个日期。

例如：

```text
一面：2026-09-20
二面：2026-09-24
HR 面：2026-09-28
```

列表卡片显示最早一轮已经确认的面试日期：

```text
2026-09-20
一面 · 二面 · HR 面
```

面试日期带有精度：完整日期按日展示；只确认到月或年的历史记录按已知部分展示（「2026年6月」「2026年」），不虚构具体日。真实面试日未确认的记录不展示日期，相关说明保留在备注中。

### 6.3 V1 不记录最终面试结果

卡片只展示真实存在的轮次：

```text
一面 · 二面 · 三面 · HR 面
```

V1 不额外增加：

- Offer；
- 一面挂；
- 二面挂；
- 流程中；
- 泡池；
- 拒 Offer。

未来如果用户明确需要“只看拿到 Offer 的面经”等能力，再新增结果字段。

### 6.4 页尾祝福「接受祝福」

列表末尾固定一条祝福区，与面经卡片视觉分离：

- 一行居中文案「愿下一封来信，是你期待已久的 Offer！」+「接受祝福」按钮 +
  「已有 N 人接受了这份祝福」计数常驻展示；
- 点击后播放礼花动效（克制配色、约一秒散尽、尊重系统减弱动效偏好），按钮变为
  「已接受」态，计数 +1；
- 一人一次：登录用户由服务端唯一约束保证（重复点击幂等返回当前总数）；游客在
  本地防重复，服务端按 IP 限流；
- 彩蛋级轻互动：不做匿名指纹、不进搜索、不做榜单。

## 7. 面经详情与阅读

### 7.1 详情基本信息

详情顶部展示：

- 公司；
- 部门（存在时）；
- 岗位；
- 招聘类型；
- 岗位分类；
- 标签；
- 首轮日期；
- 实际面试轮次；
- 来源链接（存在时）；
- 历史记录存在时，以辅助信息展示原岗位原文 / 明确记载的推断岗位 / 事实性备注，避免迁移后真实限定信息虽然入库却对用户不可见。

### 7.2 轮次结构

一份面经可以拥有多个面试轮次。

轮次从固定集合中选择，用户不发明轮次名称：

```text
一面 / 二面 / 三面 / 四面 / 五面 / HR 面
```

每份面经只包含实际发生过的轮次，不要求连续，也不要求一定存在 HR 面。

每轮独立记录：

- 轮次（固定集合之一）；
- 面试日期（可选，一个标准日期，记不清就留空）；
- 问题列表。

阅读时每轮是一个一级内容块，轮次头一行展示「轮次名 · 题数 · 日期」，正文直接铺开问题；不出现题目分组、元信息面板等额外结构。

### 7.3 问题与追问

每轮包含多个主问题。

每个主问题可以包含 0～N 条追问。

结构：

```text
一面

Q1 Redis 分布式锁怎么实现？

  追问 1：为什么使用 SETNX？
  追问 2：锁过期但业务还没执行完怎么办？
  追问 3：为什么使用 Lua？

Q2 讲一下 MVCC
```

追问必须属于对应主问题，不能与主问题平级。

同轮主问题按 Q1、Q2、Q3 展示；切换轮次后重新从 Q1 开始。

视觉规则：轮次是阅读的一级分区，每个主问题是一张轻卡片（白底细边框圆角），不做「卡片里的卡片里的卡片」——卡片内部只有问题正文、可选题目链接与追问；追问用缩进加竖线挂在主问题下方。

### 7.4 算法题与题目链接

算法题不是一种特殊的问题形态。它在用户视角下就是一道普通问题，最多额外带一个可选的「相关题目链接」。

```text
Q10 最长无重复子串

    LeetCode 3 ↗
```

- 链接来源不限于 LeetCode，也允许牛客、Codeforces 等任何题目页；
- 历史数据已明确对应 LeetCode 题号时展示「LeetCode N ↗」，否则展示链接名 ↗；
- 无法唯一确定题号时不猜题号；
- 是否属于算法题由平台根据链接与内容判断（后处理），**不要求投稿用户标注**。

## 8. 复制体验

### 8.1 单题复制

每道主问题都有始终可见的复制按钮，PC 与手机均不能依赖 Hover。

复制主问题本身，不混入 UI 文案。

### 8.2 追问复制

复制第 N 条追问时，**只复制该条追问的文本**——复制按钮复制的是它旁边的内容。

需要带上下文（主问题 + 全部追问）时使用「复制整组」。

```text
锁过期但业务没执行完怎么办？
```

### 8.3 复制整组

有追问的问题支持“复制整组”，复制主问题与所有追问。

没有追问的问题不额外显示重复的“复制整组”按钮。

### 8.4 失败处理

只有 Clipboard API 真正成功后才能提示“已复制”。

如果自动复制失败，必须提供完整可选中文本供用户手动复制，不能假提示成功。

## 9. GitHub 登录

### 9.1 登录方式

V1 使用 **GitHub OAuth**。

不建设：

- 邮箱注册；
- 密码体系；
- 找回密码；
- 短信验证码。

首次 GitHub 授权成功后自动创建本站用户。

### 9.2 为什么需要登录

登录只服务于“贡献与治理责任”，不阻碍阅读。

需要登录的能力：

- 投稿；
- 查看自己的投稿；
- 在审核通过前修改投稿；
- 发起已发布内容的修改申请；
- 发起已发布内容的删除申请。

## 10. 投稿

### 10.1 投稿必须是结构化录入

V1 **不提供 Markdown 编辑器**，也不要求用户粘贴一大段 Markdown 再由系统解析。

用户直接使用卡片式结构化表单填写面经。

### 10.2 投稿字段

一份投稿至少包含：

- 公司；
- 岗位；
- 招聘类型；
- 部门（可选，能确认时填写）；
- 标签；
- 1～N 个面试轮次（一面～五面 / HR 面）；
- 每轮面试日期（可选，标准日期选择器，记不清就留空）；
- 每轮 1～N 个主问题；
- 每个主问题 0～N 个追问；
- 每个主问题可选一个相关题目链接（见 7.4）；
- 来源链接（可选）。

投稿用户**不填写**以下整理性字段，它们由平台后处理或仅供历史数据兼容读取：

- 问题类型（普通 / 算法）；
- 题目分组 / 知识分类；
- 问题上下文说明；
- 算法题结构化描述（题干、要求、题号）;
- 日期精度（年 / 月）。

### 10.3 投稿页结构示意

```text
分享面经
────────────────────

公司 *            岗位 *
[ 小米 ▾ ]        [ 后端开发 ▾ ]

招聘类型 *        部门（可选）
[ 校招 ▾ ]        [ 抖音电商      ]

标签（可选）
[ Redis × ] [ MySQL × ] [ + 添加 ]

────────────────────

一面 · 2026-09-20 · 2 个问题           ✕

  Q1
  [ 面试官问了什么？                  ]
  [ Redis 分布式锁怎么实现？           ]

    ↳ [ 面试官接着问了什么？          ]
    ↳ ＋ 补一条追问

    ＋ 相关题目链接（可选）

  Q2
  [ 面试官问了什么？                  ]
  [ 讲一下 MVCC                      ]

  ＋ 记一道问题

────────────────────

＋ 添加下一轮面试（二面 / 三面 / … / HR 面）

────────────────────

来源链接（可选）
[ https://...                   ]

────────────────────

            保存草稿    提交审核
```

投稿体验的验收标准只问一个问题：**一个刚面完的人，能不能在 30 秒内开始写第一道题？** 核心主流程必须是「选轮次 → 写问题 → 添加追问 → 下一题」。

日期只提供标准日期选择器，不暴露「日期精度」概念；用户记不清日期时直接留空。

多轮编辑时一个轮次是一个一级内容块，新增下一轮后新轮自动展开、其余轮次可收起为一行摘要（轮次 · 日期 · 题数）。删除、排序等低频操作在 hover 时出现或收进「···」菜单，不能比问题本身更抢眼。

### 10.4 来源链接

来源链接是可选字段。

来源可以是：

- 用户自己的公开面经；
- 用户在牛客、博客、GitHub 等公开平台看到的他人面经；
- 其他可公开访问的原始来源。

提交来源链接**不等于只扔一个 URL 给管理员处理**。

用户仍然必须完成结构化面经录入，管理员不负责替投稿者从链接中重新录入全部内容。

来源链接的作用主要是：

- 溯源；
- 审核参考；
- 同源重复投稿判断。

## 11. 公司、岗位、标签新增机制

### 11.1 核心原则

**用户负责提出，管理员负责定稿。**

用户在投稿时优先从现有正式数据中搜索和选择。

如果不存在，可以直接输入一个新的候选项，不需要退出投稿流程，也不需要先单独申请。

### 11.2 用户侧交互

公司 / 岗位是**普通文本输入框**：用户直接填写名称，不需要判断目录里有没有、也不需要区分「选择已有」还是「新增」——填什么都接受。

输入时提供非强制的联想：输入「字节」时浮出「字节跳动」，点击则关联正式目录项；不理会联想直接提交也可以。

```text
公司
[ 字节                            ]
 ├ 字节跳动          ← 点击关联正式项
 └ （不点就直接提交「字节」）
```

用户填写的名称只表示：

```text
公司：字节（候选 · 随投稿一起审核）
```

并不会立即创建正式 Company，也不会因为名称与目录不同而阻止提交。

标签仍采用「搜索多选 + ＋ 新增标签」的形式：**一份投稿最多绑定 5 个正式标签**（管理员治理时遵守；超出部分由管理员归并），用户投稿时不设硬上限，但提示优先选择最能描述整份面经的标签，而不是把问题里出现过的关键词全部挂上。

正式标签体系控制在约 26 个（场景设计；后端技术：Java、Go、JVM、JUC、Spring、MySQL、Redis、MQ、网络、操作系统、Linux、Docker、ES；AI/Agent：Agent、RAG、MCP、Memory、Tool Calling、Context、Prompt、多Agent、Workflow、AI Coding、Skill、评测）。更细的概念（Kafka、AQS、HNSW、LangGraph 等）不设正式标签——它们留在问题正文里，搜索照样能搜到；用户误提的细粒度候选由管理员归并到主标签。

两个刻意排除的高频词：

- **「项目」不设标签**：出现在约四分之三的面经里，无区分度，正文搜索即可覆盖；
- **「算法」不占标签位**：它是面经的内容属性而非技术方向——「含算法题」由题目数据（questionType=ALGORITHM）派生，在详情页以轻量徽章展示，未来可直接做「含算法题」筛选，不与 Redis/MySQL 这类技术标签混排。

首页卡片标签只回答一个问题：**这份面经主要在聊什么技术/方向？**

### 11.3 投稿无需等待候选项单独审核

如果一篇投稿同时包含：

- 新公司；
- 新岗位；
- 新标签；

用户仍然可以直接提交整份面经。

不能做成：

```text
先申请公司
→ 等审核
→ 公司通过
→ 用户回来继续投稿
```

所有候选项都随整份投稿一起进入审核。

### 11.4 管理员处理方式

管理员审核时可以：

1. 选择已有正式项；
2. 修改用户填写的名称后创建新的正式项；
3. 直接创建新的正式项；
4. 对标签直接删除。

例如用户填写：

```text
公司：字节
岗位：Java后台
标签：Redis / Java多线程锁
```

管理员可以调整为：

```text
公司：字节跳动
岗位：Java 后端开发
标签：Redis / JUC
```

如果正式库里已经存在“字节跳动”，直接关联已有公司。

如果“JUC”不存在但管理员认为应该新增，则创建正式标签。

### 11.5 V1 不建设运行时 Alias / Mapping 系统

线上正式投稿后：

- 用户提出候选项；
- 管理员直接选择已有项或创建新项；
- 不自动生成“字节 → 字节跳动”之类长期运行的 Mapping 规则。

## 12. 投稿生命周期

### 12.1 核心状态

V1 保持简单：

```text
DRAFT
  ↓
PENDING_REVIEW
  ↓
  ├── PUBLISHED
  └── REJECTED

PUBLISHED ──删除申请批准──> REMOVED ──作者编辑保存──> DRAFT（复活）
```

是否需要额外的内部审核状态由后端设计阶段决定，但产品层不需要暴露复杂状态机。

### 12.1.1 Version 是工程概念，不是产品概念

数据使用 version 乐观锁与 baseVersion 基线保证并发安全（编辑期间内容被他人更新时拒绝旧提交、申请批准前核对公开内容），但这些数字**只存在于 API 与数据库，任何页面不展示**：

- 用户可见：状态、内容、提交时间、更新时间、申请内容、审核结果；
- 系统内部：version、baseVersion、Revision、Snapshot。

并发冲突的用户话术是「内容刚刚发生了更新，请刷新后再继续」，而不是版本号对比。UI 检查原则：**这是用户需要理解的概念，还是系统为了把事情做对需要的概念？后者一律藏起来**（日期精度、问题类型、版本号均属此类）。

### 12.2 审核通过前允许作者修改

正常交互规则：

> **只要尚未发布，作者都可以修改自己的投稿。**

包括：

- DRAFT；
- PENDING_REVIEW。

如果作者修改了一份正在等待审核的投稿：

- 保存最新内容；
- 保持待审核状态；
- 更新最后修改时间；
- 审核端必须能够看到最新版本，避免审核旧内容。

被拒绝的投稿在作者再次编辑保存后回到草稿状态（拒绝原因随之清空），重新提交才进入审核；提交审核只从草稿状态发起。

V1 不需要引入复杂的实时协作锁。

### 12.3 审核通过后作者不能直接修改正式内容

当投稿进入：

`PUBLISHED`

作者不能直接覆盖线上正式内容。

原因：内容已经成为公共知识库的一部分，可能已经被搜索、阅读或分享。

## 13. 管理员审核

### 13.1 管理员可以修改全部内容

管理员审核一份投稿时，可以修改：

- 公司；
- 岗位；
- 招聘类型；
- 标签；
- 轮次；
- 每轮日期；
- 主问题；
- 追问；
- 来源链接；
- 其他正式展示字段。

管理员不是只做“通过 / 拒绝”的二元操作，而是承担内容治理责任。

### 13.2 审核结果

管理员可以：

- **发布**
- **拒绝**

V1 不强制增加大量中间状态。

审核动作完成后**自动返回审核列表**：成功提示（含公开面经的入口链接）展示在列表
顶部，管理员不停留在已处理完的详情页。

### 13.3 原始投稿需要可追溯

即使管理员修改了投稿，也应保留用户提交时的原始内容或提交快照，以便：

- 审计；
- 排查误改；
- 解释为什么最终公开内容与用户原始投稿不同。

实现方式在领域模型 / 数据库阶段确定。

---

## 14. 已发布内容的修改与删除

### 14.1 修改申请

作者可以对自己已经发布的面经发起修改申请。

不能直接修改线上正式内容。

管理员审核修改申请后：

- 同意：更新正式内容；
- 拒绝：正式内容保持不变。

### 14.2 删除申请

作者可以对自己已经发布的面经发起删除申请。

不能直接删除线上内容。

管理员审核后：

- 同意：按平台删除策略处理（下架，稳定 ID 保留）；
- 拒绝：继续保留。

已下架（REMOVED）的面经，作者仍可编辑保存使其复活为草稿，重新提交审核后再次公开。

### 14.3 产品原则

**发布前：作者可自由修改。**

**发布后：通过平台治理流程修改或删除。**

## 15. 重复投稿与去重

### 15.1 什么才叫重复面经

V1 去重要解决的是：

> **同一份面经被重复投稿。**

而不是：

> **不同面经问了类似问题。**

例如：

```text
Redis 分布式锁怎么实现？
你们项目中的 Redis 分布式锁是怎么做的？
```

很多公司都会问类似问题，这些数据应该被保留，不能因为题目相似而去重。

问题重复度本身还是未来“高频问题”能力的重要数据基础。

### 15.2 V1 去重策略

V1 不做基于题目相似度的自动去重，不做 Embedding，不做 AI 语义判重。

基础规则：

#### 有来源链接

对来源 URL 做基础标准化后，发现同一个原始链接已经投稿时：

- 投稿端提示可能已存在；
- 审核端明确显示已有同源面经；
- 最终是否视为同一份，由管理员判断。

不能只因为“问题类似”自动拒绝。

#### 无来源链接

V1 不自动做语义判重。

管理员审核时发现明显是同一份内容，可以人工处理。

### 15.3 历史数据例外

同一来源帖可能对应不同候选人的不同真实流程，因此不能只凭 URL 相同直接合并记录。

## 16. 我的投稿

“我的投稿”保持轻量，不做社交个人主页。

至少展示：

- 投稿标题 / 公司 + 岗位；
- 提交时间；
- 最后修改时间；
- 当前状态；
- 编辑入口（尚未发布时）；
- 删除纯草稿（仅从未提交过审核的草稿）；
- 查看已发布面经；
- 申请修改；
- 申请删除。

状态文案应使用用户能理解的产品语言，例如：

- 草稿；
- 待审核；
- 已发布；
- 未通过。

## 17. URL、分享与公开访问

### 17.1 稳定 URL

每份已发布面经拥有稳定公开 URL：

```text
/interview/{id}
```

ID 分配后不改变、不复用。

搜索定位可以使用：

```text
/interview/{id}?q=memory#question-{questionId}
```

问题锚点必须使用稳定问题 ID，不能只依赖 Q1 / Q2 或页面位置。

### 17.2 分享

公开面经链接任何人都可以打开，不强制登录。

用户将公开链接复制给别人属于正常浏览能力，不应人为增加登录门槛。

### 17.3 列表 URL 状态

公司、岗位、招聘类型、搜索词反映到 URL，使刷新、分享、浏览器前进 / 后退能够恢复状态。

例如：

```text
/?company=bytedance&role=agent&type=intern&q=redis
```

### 17.4 返回行为

从列表进入详情再返回时，必须恢复：

- 搜索词；
- 筛选条件；
- 列表滚动位置。

## 18. PC 与 H5

### 18.1 视觉方向

简洁、克制、专业、现代，具备内容产品感。

重点始终是：

- 公司；
- 岗位；
- 轮次；
- 问题；
- 追问；
- 搜索。

避免：

- 复杂 Dashboard；
- 赛博朋克；
- 大量无意义渐变；
- 满屏统计图；
- 管理后台感；
- 过量标签；
- 过度动画。

功能与交互一律以本 PRD 为准（旧品牌视觉参考图已从仓库移除，历史由 Git 追溯）。

### 18.2 PC

- 首页可使用 2～3 列卡片；
- 搜索与筛选清晰可见；
- 详情正文保持舒适阅读宽度；
- 投稿表单按结构化内容分区；
- 审核页应能够高效查看和修改整份投稿。

### 18.3 H5

手机端必须作为 V1 首发体验，而不是事后适配。

要求：

- 卡片单列；
- 详情单列；
- 投稿表单可完整操作；
- 添加问题 / 追问 / 轮次在触屏上易用；
- 重要操作不依赖 Hover；
- 多轮导航可横向滚动；
- 长面经正文不出现无意义横向滚动；
- 搜索定位后目标内容不能被 Sticky Header 遮挡。

## 19. 页面状态与异常处理

### 19.1 浏览空状态

```text
暂时没有找到符合条件的面经
试试切换公司、岗位或招聘类型。

重置
```

重置清除：

- 公司；
- 岗位；
- 招聘类型；
- 搜索词。

### 19.2 数据加载失败

显示明确错误状态和“重新加载”。

不能无限 Loading。

### 19.3 无效详情 ID

显示：

- 面经不存在 / 已不可访问；
- 返回面经列表入口。

不能展示空白页。

### 19.4 投稿异常

投稿保存失败时：

- 不得清空用户已经输入的大量问题；
- 应明确提示失败；
- 尽可能保留当前表单内容。

### 19.5 审核期间被作者修改

如果管理员打开审核页后，作者又更新了待审核投稿：

- 审核端必须能够感知内容已变化；
- 不应静默用旧页面覆盖作者的新内容。

具体并发控制方式在后端设计阶段决定。

## 20. 关于、反馈与支持作者

### 20.1 统一入口

V1 提供一个轻量的：

> **关于 / 反馈**

入口。

它属于产品配套能力，不属于搜索、投稿、审核等核心业务，不新增独立后端模块。

入口可以放在顶部导航、用户菜单、页脚或轻量固定入口中，最终位置由 UI 实现决定；PC 与 H5 均必须可访问。

### 20.2 关于项目

入口中至少展示：

- 面个 Offer 的简短介绍；
- 开源仓库入口；
- 作者 / GitHub 信息；
- 意见反馈入口；
- 支持作者入口。

不建设传统个人主页，也不扩展为社交资料页。

### 20.3 意见反馈

V1 **不自建反馈表、反馈 API、反馈后台或回复系统**。

Bug、产品建议、数据问题统一引导到项目 GitHub Issues。

建议按 GitHub Issue Template 区分：

~~~text
Bug 反馈
功能建议
数据问题
~~~

这样可以直接使用 GitHub 的讨论、状态追踪与 PR 关联能力，避免重复建设一套反馈工单系统。

### 20.4 支持作者

如果用户认为项目有帮助，可以通过作者提供的收款二维码进行**完全自愿的赞赏**。

规则：

- 可展示微信 / 支付宝等作者主动提供的收款二维码；
- 二维码作为前端静态资源，不经过面个 Offer 后端支付系统；
- 不建设订单、支付接口、支付回调、充值记录或支付数据库；
- 赞赏不解锁任何功能，不提供会员、优先审核、特殊权限或其他权益；
- 页面需明确说明“赞赏完全自愿，不影响任何功能”。

因此“支持作者”不是 V1 的商业支付能力，只是开源项目的自愿赞赏入口。

## 21. V1 验收标准

### 21.1 浏览与搜索

- 游客无需登录即可浏览；
- 公司、岗位、招聘类型可筛选；
- 搜索可以命中具体问题和追问；
- 搜索结果可以定位到详情中的对应问题；
- 搜索关键词高亮不改变复制内容；
- 列表卡片展示公司、岗位、首轮日期与实际面试轮次；
- 不展示虚构的 Offer / 挂 / 流程中状态；
- URL 可恢复筛选与搜索状态。

### 21.2 阅读与复制

- 多轮面经结构清楚；
- 主问题与追问层级明确；
- 单题复制正确；
- 追问复制只复制该条追问文本；
- 复制整组正确；
- 自动复制失败时提供手动复制；
- PC 与手机均可正常使用。

### 21.3 登录

- GitHub OAuth 可正常授权；
- 首次授权自动创建用户；
- 游客浏览不被登录打断；
- 投稿相关能力必须登录。

### 21.4 投稿

- 用户可以结构化填写公司、岗位、招聘类型与标签；
- 可以新增多个面试轮次；
- 每轮可以独立填写日期；
- 每轮可以新增多个问题；
- 每题可以新增多个追问；
- 来源链接可选；
- 不需要 Markdown；
- 新公司 / 岗位 / 标签可以随投稿一起提交；
- 不要求用户先等待候选项审核。

### 21.5 投稿编辑

- 未发布投稿作者可以修改；
- 作者修改后管理员审核到的是最新版本；
- 已发布内容作者不能直接覆盖正式数据。

### 21.6 管理员审核

- 管理员可以查看待审核投稿；
- 管理员可以修改整份投稿的任意正式内容；
- 管理员可以选择已有公司 / 岗位 / 标签；
- 管理员可以创建新的正式公司 / 岗位 / 标签；
- 管理员可以删除不合理标签；
- 管理员可以发布或拒绝；
- 原始投稿可追溯；
- 管理员可以直接修改已发布面经，修改留有修订审计；存在待处理申请时操作被拒绝。

### 21.7 修改 / 删除申请

- 已发布投稿作者可以申请修改；
- 已发布投稿作者可以申请删除；
- 正式内容不会因为申请而立即变化；
- 管理员批准后才真正生效。

### 21.8 去重

- 不允许用“问题相似”作为面经重复判断；
- 同源 URL 可以触发重复提醒；
- 同源 URL 不直接替代管理员最终判断；
- 无来源链接时 V1 不做语义自动去重。


## 22. V1 成功标准

V1 成功不以“功能数量”衡量，而以核心闭环是否成立衡量。

### 对普通用户

用户能够：

```text
打开产品
→ 快速找到目标公司 / 岗位 / 技术点
→ 阅读真实面试问题与追问
→ 复制不会的问题继续学习
```

### 对贡献者

用户能够：

```text
GitHub 登录
→ 用结构化卡片快速录入真实面经
→ 提交审核
→ 查看状态
→ 最终形成公开面经
```

### 对平台

管理员能够：

```text
审核投稿
→ 修正内容
→ 规范公司 / 岗位 / 标签
→ 处理重复
→ 发布高质量内容
```

当这三个闭环都能稳定工作，V1 才算完成。

## 23. 后续版本方向

### AI

未来可以在单个问题旁提供：

```text
问 AI
```

AI 能力可以基于当前真实问题及其追问上下文提供：

## 24. 当前已冻结的关键决策

为避免后续本地 AI 或开发过程中重新发散，V1 当前关键决策如下：

1. **V1 是公开产品，不再只是个人工具。**
2. **核心只做搜索、阅读、投稿、审核、内容治理。**
3. **游客可以直接搜索和阅读。**
4. **GitHub OAuth 是 V1 登录方式。**
5. **投稿必须登录。**
6. **投稿使用结构化卡片，不使用 Markdown 解析。**
7. **面试时间按轮次记录，带日 / 月 / 年精度；发布时间不得冒充面试时间。**
8. **列表显示首轮日期 + 实际轮次。**
9. **V1 不记录最终 Offer / 挂 / 流程中等结果。**
10. **问题可以有 0～N 条追问。**
11. **来源链接可选，但提交链接不能替代结构化录入。**
12. **用户可以提出新公司 / 新岗位 / 新标签。**
13. **候选项不会立即进入正式库。**
14. **管理员审核整份投稿时一并处理候选项。**
15. **审核阶段管理员可以修改投稿全部内容；发布后管理员可直接修改正式内容——携带版本校验、存在待处理申请时先处理申请、修改留修订审计。**
16. **线上 V1 不建设长期 Alias / Mapping 系统。**
17. **审核通过前，作者可以修改自己的投稿。**
18. **发布后作者不能直接修改 / 删除，只能申请，由管理员审批。**
19. **去重判断的是“同一份面经”，不是“有没有相似问题”。**
20. **V1 只做基础同源 URL 重复提醒，不做语义自动去重。**
21. **评论、点赞、关注、私信、排行榜不进入 V1。**
22. **AI 问答、AI 审核、付费不进入 V1。**
23. **正式产品名为「面个 Offer」；Interview Vault / interview-vault 保留为开源工程与仓库名，不做全仓技术重命名。**
24. **V1 提供统一“关于 / 反馈”入口，反馈统一跳转 GitHub Issues，不自建反馈系统。**
25. **支持作者只提供自愿赞赏二维码，不建设站内支付，不与任何功能权益绑定。**

除产品名称外，以上规则在进入领域模型设计后原则上不再随意改动；如确需修改，应先更新本 PRD，再调整数据库、API 或前端实现。
